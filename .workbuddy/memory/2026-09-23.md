- **wfifo 机制**：写侧 `din_clk = l_clk`（每 4 拍一组 4 通道 ×16 bit 写入，`adc_valid_*` 为 per-channel valid，组写使能取 `din_valid_0`），读侧 `dout_clk = divclk`；双口 RAM（`ad_mem`，clka/clkb）+ 每 8 次写翻转 `din_req_t`，3 级 FF 同步 + 双沿检测出 1 拍脉冲 → 读侧把读地址重载为"最新一批基址"再连读 8 拍。跨域只过 1 bit；**不做速率变换**，只吸收相位（弹性缓冲），读指针允许滞后 ≤2 批（内存 16 深）。注释原文已记：`no ovf/unf handling, read-bw > write-bw (equal will NOT work)`；`din_ovf→axi_ad9361/adc_dovf`，`dout_ovf←adc_pack/fifo_wr_overflow`。
- **与 openwifi 自己做法的对比**：`adc_intf` 里 40 MHz→100 MHz 的跨域没有用 FIFO，只是两级 FF + 上升沿检测（`adc_valid_decimate` 脉冲 25 ns ≫ 100 MHz 周期 10 ns，且两时钟同源于 MMCM 才敢这么写）；`xpm_cdc_array_single` 只用于 `bb_gain`。

- **实用推论**：`divclk = fS` 且 `clk_wiz` 按 40 MHz 输入配 100 MHz 输出 ⇒ 改 `rf_init.sh` 的 40 MSPS 会连带改 PL 主频与 `board_def.v` 的 `SAMPLING_RATE_MHZ`，必须重综合。这条对用户后面的 CSI/IQ 实验（想改采样率时）是关键约束。

## 回答：mac80211 这个"框架"到底指什么（`sdr.c` 实测）

用户对入门资料 §1 名词表里 "mac80211 = Linux 内核 WiFi 协议栈框架" 这条发问。为把"框架"讲实，回读了 `driver/sdr.c`：

- `openwifi_ops`（`sdr.c:2170`，`struct ieee80211_ops`）是驱动交给内核的**回调表**，只描述硬件能力：tx / start / stop / add_interface / remove_interface / config / set_antenna / get_antenna / bss_info_changed / conf_tx / prepare_multicast / configure_filter / rfkill_poll / get_tsf / set_tsf / reset_tsf / set_rts_threshold / ampdu_action / testmode_cmd。另有两处**直接借用框架的通用实现**：`.wake_tx_queue = ieee80211_handle_wake_tx_queue`、`.add|remove|change|switch_vif_chanctx = ieee80211_emulate_*`（驱动不实现信道上下文，让框架模拟）。
- 生命周期：`ieee80211_alloc_hw(sizeof(*priv), &openwifi_ops)`（:2256）→ `ieee80211_register_hw`（:2619）→ `ieee80211_unregister_hw`（:2794）→ `ieee80211_free_hw`（:2771）。
- 向上：`ieee80211_rx_irqsafe(dev, skb)`（:617），调用前填 `rx_status`（mactime=TSF + `RX_FLAG_MACTIME_START` :586、signal/rate_idx/antenna、`RX_FLAG_FAILED_FCS_CRC`、AMPDU 细节）并 `memcpy` 进 `IEEE80211_SKB_RXCB(skb)`。
- 向下：`openwifi_tx`（:991）收到的是**已经成形、该加密该聚合都由框架处理完的 802.11 MPDU**，驱动只做 DMA 环形缓冲 + 写 tx_intf；完成经 `ieee80211_tx_status_irqsafe`（:844，另有 :988/:1093）把 PL 报回的 ACK/重传次数翻成 `IEEE80211_TX_STAT_ACK` 等标志交回框架，由框架决定重传与上报。
- 驱动声明自己支持的接口类型（:2563）：MONITOR/AP/STATION/ADHOC/MESH_POINT/OCB/P2P；`ieee80211_hw_set` 只声明能力位（RX_INCLUDES_FCS、BEACON_TX_STATUS、REPORTS_TX_ACK_STATUS、SIGNAL_DBM、AP_LINK_PS、AMPDU_AGGREGATION）。filter 的 `MONITOR_ALL` 也是框架算好交给 `openwifi_configure_filter` 的（:2104）。
- 结论口径（用户认可的方向）：驱动不是被框架"控制"，而是**控制反转**——驱动注册回调表，成为框架的硬件后端；MAC 层状态机/队列/聚合/加密/radiotap 全在框架里，硬件只保留 µs 级时序（xpu 的 CSMA/CA）与寄存器/DMA/RF。radiotap 头由 mac80211 rx 路径用 `rx_status` 组装，TSFT 即 `rx_status.mactime`。

## 回答：sample_strobe 是什么

- 定义：20 Msps 样本**有效单周期脉冲**（不是电平 valid）。数据总线 100 MHz、样本率 20 Msps ⇒ 5 拍才 1 个新样本，其余 4 拍总线保持旧值，下游无法靠"值变了"识别新样本。
- 来源链：`adc_intf` 的 `adc_valid_decimate=(adc_valid_count==0)`（40 MSPS 每 2 取 1）→ `data_to_bb_valid`（上升沿检测）→ `rx_iq_intf.rf_iq_valid`（`rx_iq_intf.v:55` 等于 `bw20_iq_valid`；`:152` 在 `slv_reg3[4]=1` 时取 FIFO 读出节奏 `rden`）→ `rx_intf` 顶层 `sample_strobe`。`bw20_iq_valid = slv_reg3[8] ? iq_valid_from_tx_intf : data_to_bb_valid`（`rx_intf.v:266`，含回环模式）。`adc_intf` 里 40→100 MHz 跨域只两级 FF + 上升沿，没用 FIFO。
- 三者共用：`openwifi_ip_ultra_scale.tcl:329` 一根网 `rx_intf_0_sample_strobe` 同时接 `openofdm_rx_0/sample_in_strobe`、`side_ch_0/sample_in_strobe`、`xpu_0/ddc_iq_valid`（`openwifi_ip.tcl:325` 无 side_ch）。⇒ 除 TSF 外，三方"第几个样本"的计数也天然同源。
- 命名惯例：openwifi 里 `strobe` = 单周期使能脉冲，`valid` = 电平型。官方 `doc/` 全目录搜不到 `sample_strobe`（只有 `fcs_in_strobe`、`pkt_header_valid_strobe` 等），此信号名只能从 RTL 得——属于"文档没有"的正当例外。
- 交付：按用户选择**只写进 §1 名词表一行**（放在"抽取"之后），不在 §3.3 展开原理。

## 追问：为什么 sample0 既直接进 openofdm_rx，又要经 xpu 再进 openofdm_rx

- **前提是错的**：`openofdm_rx` 只有一个样本入口 `sample_in`（←`sample0`）。从 xpu 回来的只有一根 `rssi_half_db[10:0]`，是**标量**，不是样本；样本从不流经 xpu。
- 抽头不是串联级：`sample0` 在 100 MHz 域里就是一根线，`xlslice_0/1` 只切 I/Q 两半送 `ddc_i`/`ddc_q`，零逻辑开销；xpu 内部只有 `rssi.v` 一条支路用它（另外 `cw_exp` 拿 `ddc_q[2]`/`ddc_i[0]` 当退避随机种子，`xpu.v:506`）。

- 好处是"一个测量值多处共用"，官方 `doc/README.md:230` 也把 reg57 的 `rssi_half_db` 列为对外观察量：openofdm_rx 功率门（vs reg2 `POWER_THRES`，`hw_def.h:228` 初值 124 ≈ −85 dBm）/ side_ch 过阈触发 + 写进 IQ 记录（`side_ch_control.v:307/569`）/ rx_intf 的 `rssi_half_db_lock_by_sig_valid` 填 16 字节头（`rx_intf.v:88/454`；**名字里的 sig_valid 是遗留叫法，实际在 `pkt_header_valid_strobe` 那拍锁存**，`rssi.v:126-128`）/ 软件读 reg57（`rssi_openwifi_show.sh`）/ xpu 自己的 CCA（`cca.v:60` vs reg8）。

## 追问：为什么算 RSSI 涉及 xpu + xpu 整体职责

- **根因**：RSSI 不是纯样本运算，是"数字幅度 + 射频增益"的合成。`rssi.v:103` = `rssi_half_db = rssi_half_db_offset(reg7[26:16]) + iq_rssi_half_db − {gpio_status_delay[6:0],1'b0}`，即减掉 AD9361 的 AGC gain index（×2 = 换算成 half-dB）。链内两级：`iq_abs_avg`（先 `dc_rm` 去 DC → 取 `i_abs`/`q_abs` → `mv_avg_dual_ch` 滑动平均 → `iq_rssi = (i_abs_mv_avg + q_abs_mv_avg)>>1`，是**平均幅度**不是功率/RMS，`iq_abs_avg.v:35-39`）→ `iq_rssi_to_db`（幅度→half-dB，0.5 dB/步，`iq_rssi_to_db.v:145` 用 `>>num_shfit_bit`，非 CORDIC）；`fifo_sample_delay` 把 `gpio_status` 按样本数延迟（reg7[6:0]）以便和 IQ 对齐。
- 因此"同时握有高速样本 + 慢速 AGC 字"的位置只能是 xpu；且 RSSI 的头号消费者是信道接入（`cca.v:60` 用 reg8 比出 ch_idle，`csma_ca` 用 DIFS/退避），测量点放 xpu 才闭环。openofdm_rx 作为外部解码器只留 `POWER_THRES`（reg2）门限、不测功率 → 接口天生"外部喂功率"。
- **xpu 顶层例化清单**（`xpu.v`，grep module 名得出）：`edge_to_flip`×4（395/402/409/416）、`tx_on_detection`(424)、`cca`(445)、`csma_ca`(466)、`cw_exp`(525)、`tx_control`(537)、`pkt_filter_ctl`(612)、`phy_rx_parse`(646)、`rssi`(691)、`time_slice_gen`(723)、`tsf_timer`(745)、`spi_module`(756，注意模块名不叫 spi)、`xpu_s_axi`(772)。`mv_avg`/`dc_rm`/`n_sym_len14_pkt` 在子模块内部。
- **`spi.v` 是 AD9361 SPI 总线的"接管/仲裁"电路**，不是通用主控：PS SPI0 的 sclk/mosi/csn 是它的输入，`assign spi_* = spif_csn==0 ? FPGA : CPU`（`spi.v:62-64`），只在 CPU 未选中片选时抢占总线发 24 bit 命令。命令值由 `boards/ip_repo_gen.tcl:56-66` **生成** `ip_repo/spi_command.v`：`grounded_rf_port=0`（默认）→ `SPI_HIGH=24'h088A01` / `SPI_LOW=24'h008A01`（控 LO 开关）；=1 → `24'hC22001`/`24'hC02001`（切 RF 端口 A/B）。`spi_module` 有 DISABLED/IDLE/ACTIVE 三态，`tx_chain_on` 边沿触发。
- 官方 xpu 寄存器表在 `openwifi/doc/README.md`（reg0~63，含 reg1 自发静音、reg5 DIFS/退避提前量、reg6 NAV/DIFS/EIFS/动态CW 开关、reg9 低 MAC 时序、reg10 BB-RF 延迟、reg11 ACK 与重传、reg13 SPI 禁用、reg19 CW、reg20-22 时间片、reg26 CTS-to-RTS、reg27 过滤、reg28-31 BSSID/MAC、reg57 RSSI 回读、reg58/59 TSF）——**以后答 xpu 问题先看这张表**。
- 交付：§3.10 改成"四组职责表 + RSSI 合成公式段 + 原 bullets"，删掉与开头重复的 CSMA bullet、与 §2 重复的抽头解释；§1 名词表 RSSI 行补"由 xpu 用样本幅度加 AGC 增益算出"。

## side_ch 为何走 tx_dma（问：为什么 side_ch 输出直接送 tx_dma）

- 命门是 **axi_dma 一个 IP = 两条方向固定的通道**（MM2S=DDR→PL、S2MM=PL→DDR），名字只反映主用途。`openwifi_ip_ultra_scale.tcl` 四条连接：`:261` axi_dma_0/MM2S→`tx_intf_0/s00_axis`；`:277` axi_dma_1/S2MM←`rx_intf_0/m00_axis`；`:264` axi_dma_1/MM2S→`side_ch_0/s00_axis`；`:278` axi_dma_0/S2MM←`side_ch_0/m00_axis`。
- 即 **`rx_dma`(axi_dma_1) 的 MM2S 空闲 → 给 side_ch 下命令；`tx_dma`(axi_dma_0) 的 S2MM 空闲 → 收 side_ch 数据**。rx_dma 的 S2MM 已被 rx_intf 独占（一个 S2MM 只能一个源），side_ch 要进 DDR 只能借 tx_dma 的 S2MM。四条通道正好两两互补，不用加第三块 DMA（e310v2 SMALL_FPGA）。
- 软件侧佐证：dts `sdr`（:902）`dmas=<&rx_dma 1>,<&tx_dma 0>` 配名 `rx_dma_s2mm`/`tx_dma_mm2s`；`side_ch_0`（:1024）`dmas=<&rx_dma 0>,<&tx_dma 1>` 配名 `rx_dma_mm2s`/`tx_dma_s2mm` → **channel 号 0=MM2S、1=S2MM**。

## 驱动分层（问：各个 IP 的驱动的作用）

- **只有 `sdr.ko` 是 Linux 意义的设备驱动**（mac80211 后端，`ieee80211_ops` + 中断 + 设备节点），**不 EXPORT_SYMBOL**；用户态入口两条：sdrctl（nl80211 testmode，`sdrctl_intf.c` 的 `openwifi_testmode_cmd()`）+ sysfs（`sysfs_intf.c`，驱动变量映射成文件）。
- **5 个组件驱动全部是 platform_driver + `EXPORT_SYMBOL(xxx_api)`**：dts 里各有独立节点（`sdr,tx_intf`@83c00000 / `sdr,openofdm_tx`@83c10000 / `sdr,rx_intf`@83c20000 / `sdr,openofdm_rx`@83c30000 / `sdr,xpu`@83c40000，dts:974-1015），probe 里 `devm_ioremap_resource` 拿基址，导出 `tx_intf_api`/`rx_intf_api`/`openofdm_tx_api`/`openofdm_rx_api`/`xpu_api` 给 sdr.ko 调。**不建 /dev 节点**，用户态碰不到。
- **`side_ch.ko` 独立**：platform_driver（`sdr,side_ch`@83c50000）但额外注册 **netlink socket** 给用户态 `side_ch_ctl`（`user_space/side_ch_ctl_src/`，用 netlink 不用 ioctl）；sdr.c 里完全不提 side_ch。走 `side_ch/Makefile` + `make_driver.sh` 单独构建，不在顶层 Makefile。
- **加载顺序**（`user_space/wgd.sh`）：`ad9361_drv.ko` → `xilinx_dma.ko` → `modprobe mac80211` → `MODULE_ALL="tx_intf rx_intf openofdm_tx openofdm_rx xpu sdr"`（:273，**组件先、sdr 后**，因 sdr 依赖其导出符号）。`xilinx_dma.ko`/`ad9361_drv.ko`/`cf_axi_adc.ko`/`cf_axi_dds_drv.ko` 非 openwifi 自研（Xilinx/ADI）。
- 设计动机：一个 IP 一个驱动 = 寄存器访问模块化，避免 2810 行的 sdr.c 再膨胀；openofdm_rx/tx 是外部子模块，独立成 api 便于跟上游。

## E316 上 AD9361 的两条访问路线（答"普通驱动有什么用"）

- **ADI/IIO 路线**：`ad9361-phy@0` on `spi@e0006000`（PS SPI0，dts:246-255，compatible `adi,ad9361`）由 `ad9361_drv.ko` 管配置（IIO 口：`iio_attr -d ad9361-phy ...`）；`cf-ad9361-lpc@79020000`（`adi,axi-ad9361-6.00.a`，dts:1029）+ `cf-ad9361-dds-core-lpc@79024000`（dds 版，dts:1038）由 `cf_axi_adc.ko`/`cf_axi_dds_drv.ko` 管，**但 e310v2 上它读不出 IQ**：`dmas`/`dma-names` 被注释（dts:1032-1033）、BD 无 `axi_ad9361_adc_dma`，只能读寄存器。**修正此前"libiio 能读 40 MSPS 原始 IQ"的错误说法。**
- **openwifi 路线**：`sdr.ko` → 20 Msps 带 TSF 的帧/IQ。
- **唯一硬冲突 = SPI0 总线**：这正是 xpu 需要 `spi_module` 抢总线（CPU 未拉片选时插 24 bit 命令开关 TX LO）的根因。
- "驱动"与"库"的判据：普通驱动 = 向子系统注册（dmaengine/IIO/spi/netdev）+ 对外提供标准 API；openwifi 那 5 个只 `ioremap` + `EXPORT_SYMBOL(*_api)`，**没注册任何子系统**，`/dev`、`/sys` 里都没有入口。

## monitor / 正常模式 = iftype（不是运行时开关）

- 词源是 openwifi 脚本名：`user_space/nic_back_to_normal.sh` 执行 `iwconfig mode managed`（= `NL80211_IFTYPE_STATION`）；`monitor_ch.sh` 执行 `iw dev X set type monitor`（= `NL80211_IFTYPE_MONITOR`）。**先 `ip link set down` 才能改**，mac80211 不允许 up 状态切 iftype。
- 驱动声明支持的 iftype 共 8 种：`sdr.c:2562`（MONITOR / P2P_GO / P2P_CLIENT / AP / STATION / ADHOC / MESH_POINT / OCB）。
- **openwifi 的 monitor 是两级开关**：① mac80211 rx 路径按 iftype 分流（monitor 不做协议处理，上送时附 radiotap）；② FPGA 过滤 —— `openwifi_configure_filter` 把 flag 写进 `xpu/pkt_filter_ctl.v`。
- **mac80211 不直接告知驱动 iftype**，驱动只能靠 `(filter_flag&0xf0)==0xf0`（`FIF_BCN_PRBRESP_PROMISC|FIF_CONTROL|FIF_OTHER_BSS|FIF_PSPOLL` 四位全置）反推 monitor（`sdr.c:2103`），据此置 `MONITOR_ALL = 1<<13`（`hw_def.h:312`）。官方口径见 `openwifi/doc/README.md:242`。
- **可绕过 iftype 单独开硬件级全收**：`set_rx_monitor_all.sh` → sysfs `rx_monitor_all` → `sdr.c:2113`（store 在 `sysfs_intf.c:709`）→ 置 `MONITOR_ALL`。所以 AP 模式下也能把全部包（含 CRC 错、ACK）送 ARM；这也是官方说 CSI 功能不限于 monitor 模式（`doc/app_notes/csi.md:129`）的那一级。
- 已按"最小修订"补进文档 §3.9（行 346-350）：两个词标为 iftype + 设置方式 + 脚本出处；新增 FPGA 过滤那条 bullet。§1 名词表 radiotap 条目未动。

## DDR 缓冲 → 哪个 ko，怎么决定（用户问）

- **没有"分发"这一步**：解码帧的 AXIS 源是 `rx_intf_0/m00_axis`（接 `rx_dma` S2MM），CSI/IQ 的源是 `side_ch_0/m00_axis`（接 `tx_dma` S2MM），在 PL 连线时就定死了。
- **绑定是启动时按设备树名字认领的**：`sdr.ko` → `dma_request_chan(dev,"rx_dma_s2mm")`（`sdr.c:1661`）+ `"tx_dma_mm2s"`（`:1671`）；`side_ch.ko` → `"tx_dma_s2mm"`（`side_ch.c:603`）。各自申请自己的通道与缓冲区，互不知道对方存在。
- dts 权威绑定（`devicetree.dts:900-904` / `1019-1027`）：`sdr` 节点 `dmas=<&rx_dma 1 &tx_dma 0>`；`side_ch` 节点 `dmas=<&rx_dma 0 &tx_dma 1>`。通道号 0=MM2S、1=S2MM，由 `dma-names` 坐实。
- **发现文档 §3.7 表格末行不准确**：写 `rx_dma` MM2S 是 "`side_ch.ko`：往 side_ch 送数据"，但 `side_ch.c:596-602` 里 `chan_to_pl = dma_request_slave_channel(...,"rx_dma_mm2s")` **整段是注释**，驱动未启用。BD 连线在，驱动侧没申请。
- 唯一的运行时选择在 side_ch 内部：CSI 与 IQ 共用同一条 `tx_dma` S2MM，靠 `iq_capture`（`side_ch_control.v:313` 的 2:1 mux）切换。
- 用户尚未决定是否改 §3.7 与框图（DDR 一个框易被读成"同一块缓冲分发给两个 ko"）。

## 三类数据的共时性（用户问"能同时拿几个"）

- **最多两样：帧 + （CSI 或 IQ）**。帧 + CSI ✓、帧 + IQ ✓、CSI + IQ ✗、三者 ✗。
- 官方原文（`doc/app_notes/iq.md:212`）："You need to specify **iq_len_init** explicitly to turn on IQ capture, **which will turn off the default CSI mode**. Insert the side_ch.ko without any parameter will run the default CSI mode." → 二选一由 `insmod side_ch.ko` 的参数决定。
- 帧能与二者并行的官方依据：`doc/app_notes/csi.md:135`（"capture WiFi packets **while** capturing CSI"，靠 TSF 对齐）与 `iq.md:230`（IQ 也可在 AP-Client/ad-hoc 下跑）。
- 机制：帧走 `rx_dma` S2MM（`sdr.ko`）、CSI/IQ 走 `tx_dma` S2MM（`side_ch.ko`）——两条独立 DMA/缓冲/模块；而 CSI 与 IQ 共用 side_ch 的单 FIFO/单 DMA + 2:1 mux（`side_ch_control.v:313`）。
- **是搬运层取舍，不是数据源限制**（`sample0` 本就同时喂三方）；改并存需双 FIFO，e310v2 是 SMALL_FPGA 吃 BRAM。
- 上层入口：帧 `tcpdump -i sdr0`；CSI `side_ch_ctl g` + `side_info_display.py`；IQ `side_ch_ctl g` + `iq_capture.py`（均在 `openwifi/user_space/side_ch_ctl_src/`）。
- IQ 长度：7Z020（e310v2）≤ **4095**；大板 1~8187（`iq.md:207`，本机 MEMORY 旧记"≤4095≈204.75 µs"一致）。
- **文档 §6 缺口**：只讲了"三者为什么能对齐"，没讲"不能三者同时"，开头"上位机能拿到的三样东西"易被读成可并存。已向用户提议补一句，待定。

## 澄清：帧数据不进 side_ch（用户误以为进）

- side_ch 的数据输入只有两类，都是**样本域**的：① `sample0_in` / `sample1_in`（tcl:327-328，与 openofdm_rx/sample_in 同一根网）；② `openofdm_rx_0` 的解调中间量 `csi` / `csi_valid` / `equalizer` / `equalizer_valid` / `ofdm_symbol_eq_out_pulse`（tcl:291-295/305）。
- 其余进 side_ch 的全是控制/状态信号：过滤条件 `FC_DI` / `addr1~3`（来自 `xpu_0/phy_rx_parse`，tcl:368-376）、时序（`pkt_header_valid_strobe`/`fcs_in_strobe`/前导检测）、`tsf_runtime_val`、`rssi_half_db`、`gpio_status`、TX 侧状态、`s00_axis`（来自 axi_dma_1 MM2S）。
- **side_ch 上没有任何 `pl_to_m_axis` / 帧字节流的输入端口**。帧走 `openofdm_rx.byte_out` → `rx_intf_0/pl_to_m_axis` → `rx_dma` S2MM。
- 关键区分：**帧与 CSI 是 openofdm_rx 里同一解调过程的两个产物，在解码器内部就分岔**（帧字节流→rx_intf；equalizer 信道估计→side_ch），不是"帧先进 side_ch 再出来"。
- `pkt_len` / `pkt_rate` / `fcs_ok` 是解码器输出的状态量，也不是帧内容。文档 §3.11"输入分两类"的表述本身正确，用户是理解有误。

## 同时取帧 + CSI/IQ 的操作形态

- **两套独立入口，得同时开**：帧 = `sdr.ko`（`rx_dma` S2MM）→ mac80211 → `sdr0` 接口 → `tcpdump -i sdr0`；CSI/IQ = `side_ch.ko`（`tx_dma` S2MM）→ **经 UDP 推到 PC**。
- **交付方式不同**：帧是"设备式"（走网络栈，tcpdump 抓）；CSI/IQ 是"推送式"——`side_ch_ctl g`（可带 `-s <PC_IP>`，默认 192.168.10.2）启动，`side_ch.ko` 直接把 DDR 记录用 UDP 发出；**PC 端监听**：`iq_capture.py` 默认 `UDP_IP=192.168.10.1` / `UDP_PORT=4000`（`iq_capture.py:84-98`），CSI 用 `side_info_display.py`。**不是读本地 /dev 节点**。
- 官方 quick start（`csi.md:12-38`）顺序：板 `./monitor_ch.sh sdr0 11` → `insmod side_ch.ko` → `./side_ch_ctl g`；PC 另开终端跑 `python3 side_info_display.py`。板输出 "loop N side info count M" 中 M 递增表示数据在流。
- 两模块可同时 insmod（独立 DMA/缓冲）；对齐靠 TSF（`csi.md:135`）。

## CSI 与 IQ 各自的"触发"（用户问）

- **CSI 没有"触发"这回事**：`csi` / `csi_valid` 是 `openofdm_rx` 均衡器的持续输出（解调副产品，每包都有）。`side_ch` 做的是**过滤**——6 态 FSM 按 FC→addr1→addr2 逐级匹配（`reg1[14:12]` 选哪几级参与，`wh1h4001`/`wh5h`/`wh6h`/`wh7h`），过了就等 `last_ofdm_symbol_flag` 存进 FIFO。
- **IQ 是事件触发**：`iq_trigger_select`(reg8) 32 选 1，命中后记 `iq_len` 个样本（触发点前 `pre_trigger_len` 个）。触发源分类（官方表 `iq.md:100-131`）：FCS 结果(1 pass/2 fail)、SIGNAL 校验(4-7)、前导(8/9)、RSSI 过阈(10/11)、AGC(12-15)、TX 状态机/phy_tx_started/done(16-24,26,27)、addr 匹配(25)、对侧天线 IQ 超阈(28-31)。默认 reg8=0 = FCS 时刻。free running = `wh8d0` + `wh5d1`。阈值寄存器：RSSI `wh9dY`(0~2047)、AGC `wh10dY`(0~127)。
- **关键限制**：`side_ch_ctl g` 是**每 100 ms 重新武装一次**（`gN` → N ms），即"每 100 ms 最多抓一段"，不是每包都抓 → 大量帧没有对应 IQ。
- **找不到对应数据的常见情形**：① IQ 100 ms 周期 + 一次武装只抓一次；② 触发源选 RSSI/AGC/free running 时与包无关；③ CSI 与 IQ 互斥，另一模式缺席；④ `iq_len`≤4095（≈204 µs），长包装不下；⑤ CSI 设了 addr 过滤时不匹配的包没有；⑥ 解调失败（前导都没检出）的包无 CSI；⑦ UDP 丢包（PC `SO_RCVBUF` 仅 464 B）。
- **配对策略**：帧↔CSI 默认近似 1:1，TSF 相等即可配；帧↔IQ 要选触发源 1/2（让触发点=FCS 时刻）再**按区间匹配**，因为 IQ 记录的 TSF 是触发时刻、本身不等于任何包的 TSF。

## 结论：上位机拿不到"全部 IQ"（用户确认理解）

- **量级**：20 Msps × 32 bit（I/Q 各 16 bit）= **80 MB/s** 连续。经 `tx_dma` S2MM → DDR → UDP 到 PC 不可能持续。`iq_capture.py` 把 `SO_RCVBUF` 设成 464 B（注释 "for low latency"），本就不是为吞吐设计的。
- **四层独立限制**：① BRAM 单次记录上限（e310v2=7Z020，`iq_len ≤ 4095` ≈ 204 µs）；② `side_ch_ctl g` 每 100 ms 才武装一次；③ CSI/IQ 模式互斥 + `block_rx_dma_to_ps` 忙时掐通路；④ 一次武装通常只抓一段。
- **比例**：100 ms 有 2,000,000 个样本，最多抓 4095 → **约 0.2%**。改 `gN` 到 1 ms 也只能到 ~20%，且 1 ms 内完不成 DMA+UDP+重新武装。
- **定位**：IQ 抓取是"事件快照/调试工具"，不是连续采集流。可行的是"针对特定事件（如某 MAC 的包）逐个抓快照 + 多次重复实验"。
- **【已修正】此前以为"另一条路（ADI IIO / `cf-ad9361-lpc` + libiio）能拿 40 MSPS 连续 IQ"——错**。e310v2 上这条路的数据面是断的（BD 无 ADC DMA、dts `dmas` 注释），见本文件上面 ADI/IIO 那条。正确结论：**原始 IQ 的唯一出口就是 side_ch 的 BRAM 快照，没有任何连续通路**。"全部 IQ 到上位机"在现有 bitstream 下**根本不存在通路**，不只是带宽问题。
- **帧数据"到上位机"的方式与 CSI/IQ 根本不同**：帧**没有推送机制**，它在 `sdr.ko` 交 mac80211 后变成标准内核网卡 `sdr0`，是"挂成设备"不是"发出去"。openwifi 架构里真正的"上位机"就是**板载 Linux 自己**（mac80211 之上即协议栈），`tcpdump -i sdr0`/`hostapd`/`iperf3` 都在板上跑。要到外部 PC 只能主动取：①板上 `tcpdump -i sdr0 -w x.pcap` + `scp` 回 PC（官方 `inject_80211.md:139-143` 就是这个）；②PC 当空口客户端用自己网卡收（只得自己的帧）；③`bridge`/转发让帧从 eth0 出去（`post_config.sh:60` 装了 bridge-utils）——只转发以 PC 为目的的帧，不是全量。**想拿全量空口帧（他人帧/ACK/CRC 错帧）**：板上 `iw dev sdr0 interface add mon0 type monitor && ifconfig mon0 up` + FPGA `MONITOR_ALL` + `tcpdump -i mon0 -w trace.pcap`，仍在板上。`user_space/` 里**无任何帧转发/推送脚本**（只有 IQ/CSI 有 UDP 推送）。AP 段 `192.168.13.0/24`（`dhcpd.conf`，gw .1，client `192.168.13.2`），PC/板 管理链路是 `192.168.10.1`/`.122`（eth0）。
- **"实时把帧推给 PC" 可行，但要自搭 pcap 隧道**（帧是 802.11 链路层、网线是 802.3，不能直接互发）：板上 `tcpdump -i mon0 -U -s 65535 -w -`，PC 端 `ssh root@192.168.10.122 '...' | wireshark -k -i -`（标准 Linux 远程抓包，板是普通 Linux 一样用）。官方 Discussion #344 给的是"事后取"版：板上 `tcpdump -i sdr0 -s 65535 -w openwifi.pcap` → scp 回 PC；`sdr0` 被占用时用 `iw dev sdr0 interface add mon0 type monitor && ifconfig mon0 up` 再抓 `mon0`（驱动 `MAX_NUM_VIF=4`）。**不受限的地方**：帧这条路是连续流、速率就是普通 WiFi 量级，不像 IQ 被 BRAM/100 ms 卡死。**物理上限**（非过滤）：① `openofdm_rx` 只吃 `sample0`，**只解 RX0 一根天线**，`sample1` 只接 side_ch；② 只有当前信道；③ 只有解码器解得出的包（前导都检不出就没有这份数据；CRC 错帧能拿，`MONITOR_ALL` 含 fcs fail）。**bridge sdr0↔eth0 是另一件事**（让 PC 接进 openwifi 网络跟客户端通信），给的是普通业务流量不是全量空口帧。
- **radiotap 的物理层信息从哪来（闭环）**：驱动"剥 16 字节头"不是丢信息，是**换装**——`sdr.c:585` `skb_put_data(skb,pdata_tmp+16,len)` 剥头的同时，`:587-614` 把 signal/mactime/rate_idx/fcs_ok/short_gi 读出来填进 `rx_status`，`:616` `memcpy(IEEE80211_SKB_RXCB(skb),&rx_status,...)` 塞进 **skb->cb**（48 B 带外区，原本被 DMA 层当 `dma_dsts`，此拍被征用；代码注释原话 "from now on skb->cb is not dma_dsts any more"），`:617` 交 mac80211。
- radiotap 由 `net/mac80211/radiotap.c` 的 `ieee80211_add_rx_radiotap()` 按 `rx_status` 的有效位**重新生成**，不是把硬件头原样搬：`mactime`→`TSFT`、`signal`→`dBm Antenna Signal`、`RX_FLAG_FAILED_FCS_CRC`→`Flags.BADFCS`、`rate_idx/encoding/bw/enc_flags`→`MCS`|`Rate`|`Channel`、`antenna`→`Antenna`。**推论：硬件头里的 AGC 增益/`phase_offset`/`ch_idle` 在内核无对应字段，永远进不了 radiotap。** skb->cb 生命周期止于无线栈内（转 802.3 后 cb 归别层）→ 这就是 radiotap 必须在 mac80211 内生成的原因。
- **"能不能把全量原始 IQ 送到上位机"的完整答案（三层）**：① **通路层**：现有 bitstream 下**没有通路**——ADC 数据出 `util_ad9361_adc_pack` 后只能进 `openwifi_ip/adc_data`，ADI 的 ADC DMA 不存在（BD 无实例 + dts `dmas` 注释），所以唯一出口是 side_ch BRAM 快照。② **带宽层**：假使把 ADC DMA 加回去，仍需重综合 PL，且**网线吃不下**——单 RX 通道 = 32 bit × 40 MSPS = **1.28 Gbps** > 千兆实测 ~940 Mbps；2R2T 全量 = 2.56 Gbps。降采样到单通道 10 MSPS（320 Mbps）才可传。③ **对比**：帧能全量是因为解码器已把它压成"每包几百字节"（几 Mbps 量级），与原始 IQ 差约 **3 个数量级**。⇒ 想要长时 IQ 的现实形态是**板上存盘**（也要先改 PL 加 DMA 直出，且 SD/eMMC 写入速度需够）。
